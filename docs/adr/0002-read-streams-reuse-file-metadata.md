# Read streams reuse the file's metadata instead of calling OpenRead

`AzureBlobItemInfo.CreateReadStream()` used to return `BlobClient.OpenRead()`. Before it returns a stream, `OpenRead()` always makes a synchronous `GetProperties` request to get the blob's ETag and length ([#98](https://github.com/umbraco/Umbraco.StorageProviders/issues/98)). The `AzureBlobItemInfo` already holds those properties, often from the metadata cache, so every media response paid a second, blocking round trip that the cache couldn't remove. We decided that the read stream is built from the properties the item already has. Creating it makes no request. Reads download the blob in ranges of up to 4 MiB, the same size `OpenRead()` uses, starting at the current position, with `If-Match` set to the item's ETag. Seeking makes no request either: the next read continues the open download if it's at the same position, and otherwise starts a new range there. The first 4 KiB read are kept, so a caller that reads a header and seeks back to it doesn't download it again. When a download finds the blob was replaced (`412 Precondition Failed`) or deleted (`404 Not Found`), the metadata cache entry for that blob is evicted.

## Considered options

- **Keep `OpenRead()` and pass the known ETag in `BlobOpenReadOptions`.** Doesn't help: `OpenRead()` makes the `GetProperties` request whatever options it's given.
- **Call `DownloadStreaming()` in `CreateReadStream()`.** Replaces the HEAD with a GET, but still makes a synchronous round trip on the request thread, because `IFileInfo.CreateReadStream()` is synchronous.
- **Don't send `If-Match`, so a replaced blob is served as its current version.** Rejected: the response headers (`Content-Length`, `Last-Modified`, `ETag`) come from the item's metadata. A body from a different version would be truncated or overrun, or served under the old validators and cached as the old version.
- **Download the rest of the blob in one open-ended request.** Fewer requests for blobs over 4 MiB, but Blob Storage rejects transactional MD5 validation (an opt-in client setting) for a range without an end or over 4 MiB, and a range request that reads a few bytes would leave the whole remainder of the blob open.

## Consequences

- A media response served by `StaticFileMiddleware` makes no synchronous blob requests once the metadata is cached, and one asynchronous request per 4 MiB of content.
- Image processing still makes one synchronous request: ImageSharp reads the image header synchronously. That request also serves the rest of the image, so processing an image of up to 4 MiB makes one request where `OpenRead()` made a HEAD and a ranged GET, both synchronous.
- A blob replaced or deleted outside this instance (another server, or directly through the SDK) while its metadata is still cached fails to download with a 412 or 404. When that happens on the first range, the request returns a 500 before any of the body is sent; a blob over 4 MiB replaced while it's being streamed fails on a later range and the response is aborted, as with `OpenRead()`. This applies to processed images as well as plain files. The failure evicts the cache entry, so the next request on that server fetches fresh metadata and succeeds (or returns a 404). Before, plain files in the same window were sent under the old `Content-Length`, so a replacement of a different size produced a truncated or aborted response, while processed images were read from the new content.
- Callers that read synchronously still block, on the download instead of on `GetProperties`.
- A range request over-fetches up to 4 MiB past its start, as `OpenRead()` did. The SDK's retriable stream resumes from the current offset, under the same `If-Match`, if a connection drops partway.
